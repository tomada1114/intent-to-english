# Managing Dependencies

**Owns:** whether a package, Python or JavaScript, may exist in this repository, which
group or workspace member it joins, how its version is declared and locked, the
supply-chain window (`exclude-newer`, and pnpm's `minimumReleaseAge`), and the
exceptions `pnpm-workspace.yaml` admits. **Does not own:** landing a Dependabot pull
request, a `uv` or `npm` one included (`merging-dependency-prs`); the design
description a runtime dependency rewrites (`AGENTS.md`'s "Before changing the
architecture"); editing a security workflow or loosening a policy key (`changing-gates`).

## A new package is a sign-off change

Any new package — runtime or dev — needs the review record below and the owner's yes
**before** `uv add` or `pnpm add` runs. Propose it with the record and stop; a decline
ends the change. Routine development scope does not settle that separate decision
(AGENTS.md's "Task scope and confirmations"). A
bump inside an existing range and a removal are not new packages; they follow the update
path below.

## The review record

Adding a dependency is a lasting supply-chain commitment, so the proposal, and then the
pull request that adds the package, carries every item. A missing item means the review
has not happened yet.

- **Why the standard library or a small helper cannot do it.** The scripts under
  `scripts/` parse YAML and call GitHub without a dependency for exactly this reason.
- **Active maintenance** — recent releases, an answered issue tracker.
- **A compatible license**: MIT, BSD, or Apache. For a runtime package,
  `.github/workflows/dependency-review.yml`'s `allow-licenses` list is what CI enforces,
  over `uv.lock` and `pnpm-lock.yaml` alike; a package outside it does not merge.
- **Minimal transitive dependencies** — count what the lock gains (`uv.lock`'s
  `[[package]]` entries, `pnpm-lock.yaml`'s `packages:`), not only the direct entry.
- **Runs on the toolchain**: Python 3.14 support (`requires-python`) and wheels for the
  platforms CI and contributors use, rather than a source build; for a JavaScript
  package, Node.js 24, and any install script it wants (`allowBuilds`, below).
- **Open advisories** against the version that will resolve.
- **Its group, and why.** A runtime package is also a design change: the same pull
  request rewrites the present-state description, per `AGENTS.md`'s "Before changing
  the architecture".

## Groups and ranges

- Runtime dependencies go under `backend/pyproject.toml`'s `[project] dependencies`;
  everything only development needs goes under the root `pyproject.toml`'s
  `[dependency-groups] dev`, which the whole workspace shares. A new group needs a
  reason — CI installs `--group dev` only.
- A runtime package only some deployments need goes in an extra under
  `backend/pyproject.toml`'s `[project.optional-dependencies]`, never in a group: a
  group is not part of a built package, so a deployment could not ask for it. Code that
  needs an extra's package imports it lazily and fails with a message naming the extra.
- Declare a range, `>=X.Y`, never an exact pin; `uv.lock` pins the exact versions.
- Add from the repository root with `uv add --package intent-to-english <package>` (runtime;
  `--optional <extra>` for an extra) or `uv add --group dev <package>`, rather than typing a
  version: under the window below, a hand-typed recent version may not resolve. A bare
  `uv add <package>` at the root fails, since the virtual workspace root has no
  `[project]` table (observed with `uv add --frozen`, 2026-10-08).

## `uv.lock`

- Generated by `uv lock` at the root for the whole workspace, never hand-edited, and
  committed in the same commit as the `pyproject.toml` or `backend/pyproject.toml`
  change that caused it. **BACKGROUND:** `smart-commit`'s "Group".
- `just lock` runs `uv lock`; `just lock-check` (`uv lock --check`, the first step of
  `just verify`) fails when the lock no longer matches either manifest. Every recipe
  and CI step that runs project code passes `--locked`, which refuses a stale lock
  instead of rewriting it.

After any dependency change:

```bash
uv lock
uv sync --all-groups --locked
uv run --locked --directory backend pytest tests/<layer>/   # the app layer that uses it
just verify
```

## The `exclude-newer` window

`[tool.uv] exclude-newer = "7 days"`, in the root `pyproject.toml` (uv reads `[tool.uv]`
from the workspace root only), makes `uv lock` and `uv sync` ignore any package
version published less than 7 days ago, so a dependency cannot be resolved until it has
survived in the wild for a while. The value is relative: `uv lock` records it in
`uv.lock` as `exclude-newer-span = "P7D"` and resolves it against the current time, and
locked versions move only when the lock is re-resolved (`--upgrade`, a changed
dependency), so `uv lock --check` stays stable from one day to the next.

### How updates arrive

**Dependabot proposes, a human merges via `merging-dependency-prs`.** The `uv` entry in
`.github/dependabot.yml` runs monthly with `cooldown.default-days: 7`: one grouped PR
for minor and patch updates and one PR per major, labelled `dependencies`. Each always
moves `uv.lock`, and moves the manifest that declares a package (`backend/pyproject.toml`
or the root `pyproject.toml`) too when it raises that package's range. The cooldown
equals `exclude-newer` on purpose — uv's Dependabot guide recommends it — so Dependabot
almost never proposes a version the window refuses to lock. The edge remains: uv judges
each artifact's upload time against now minus 7 × 24 hours, while the cooldown counts
days since the release, so a wheel uploaded days after its release, or a release on the
boundary day, can still disagree. That shows as a failed Dependabot job, not as a PR
(`merging-dependency-prs`' failure mode F3). Change the two together or not at all;
shortening either loosens a gate, which is the owner's decision.

Why: the update path used to be a monthly hand move of a fixed cutoff date, and a
procedure that depends on someone remembering it does not hold. A relative window leaves
no date to move, and the floor still bounds what a hand-run command resolves.

- **A hand-run upgrade stays allowed** — before a release, or to take one package early
  within the window: `uv lock --upgrade` or `uv lock --upgrade-package <package>`, then
  `just check` and `just verify`, then the changed manifests and `uv.lock` in one commit
  of their own. The same 7-day window bounds it.
- **Security fixes arrive through the Security Fixes workflow, not Dependabot.**
  Dependabot security updates skip their cooldown but not the window, so a fix younger
  than 7 days never locks in their job, and this repository leaves them off.
  `.github/workflows/security-fixes.yml` takes their place for `uv.lock` and
  `pnpm-lock.yaml` alike (below).

### Security fixes and the one-package exception

The advisory is the trust signal: only the fix version it names — its first patched
version — may skip the window, never the latest release and never a whole package.
Daily, `.github/workflows/security-fixes.yml` runs `scripts/security_fixes.py` over the
open Dependabot alerts and opens at most one pull request; the owner merges it,
nothing merges on its own.

- **A fix older than the window** is locked as is: `uv lock --upgrade-package <package>`,
  which the window still bounds, so it may lock a later release than the fix.
- **A fix inside the window** first gets an exception in the root `pyproject.toml`'s
  `[tool.uv.exclude-newer-package]` table: `<package> = "<cutoff>"`, an absolute
  timestamp a second past the fix's last upload, so the fix locks and nothing published
  after it does. Its comment names the advisories and the day the window admits the fix.
- **The workflow drops an entry** on its first run after that day, and only while
  `uv lock` keeps every locked version without it. A stale entry would freeze the
  package at its cutoff, so dropping it is never a judgment call; dropping it early
  would move the lock back to a vulnerable version (observed with `uv lock`, 2026-10-25).
- **It stops instead of widening anything.** A fix a dependent's range holds back, or one
  that needs another too-new package, fails the run (`ERR_FIXES_UNRESOLVED`,
  `ERR_FIXES_LOCK`); a new locked package lands in the pull request under "Needs the
  owner's review" and needs the review record above before it merges.

Never add a blanket exception or shorten the window to let one package through, by hand
or in the script. How the workflow runs, the owner's one-time setup, and a manual run:
[references/security-fixes.md](references/security-fixes.md).

## The JavaScript side

The same rules hold for pnpm, with its own commands and policy file:
[references/pnpm.md](references/pnpm.md) — `pnpm --dir frontend add` or
`pnpm --dir e2e add` into the right workspace member, the caret range with pre-1.0
packages pinned exactly, `pnpm-lock.yaml` committed with its `package.json`, the window
(`pnpm-workspace.yaml`'s `minimumReleaseAge`, equal to the Dependabot `npm` cooldown),
`minimumReleaseAgeExclude` as the one-package exception, and `allowBuilds`,
`trustPolicyExclude`, `overrides`, and `peerDependencyRules` entries as reviewed
exceptions. Read it before any `pnpm add` or `pnpm-workspace.yaml` edit.

## What the scanners catch

- **OSV-Scanner** (`.github/workflows/osv-scanner.yml`) scans `uv.lock` and
  `pnpm-lock.yaml` on every pull request or push to `main` that touches either, and
  weekly: a known advisory against a version already locked, which the window cannot
  catch.
- **Dependency Review** (`.github/workflows/dependency-review.yml`) judges the packages a
  pull request changes, Python or JavaScript: a new advisory or a license outside its
  allow-list. GitHub's dependency graph reads `pnpm-lock.yaml`, so the frontend needs no
  license script of its own. Its `fail-on-scopes: runtime` means only a runtime package
  fails it, so `devDependencies` are meant to pass like the Python dev group; the action
  documents that option for vulnerabilities only, so whether it also scopes the license
  check of a pnpm entry is unchecked until a run on a frontend change shows it.
- **Dependabot alerts** read the same dependency graph, `pnpm-lock.yaml` included, once
  the owner turns them on (`starting-an-app`); the Security Fixes workflow acts on them.
- **The windows** (`exclude-newer`, `minimumReleaseAge`) catch the opposite case: a
  version too new to have a track record, advisory or not. None of these substitutes
  for another.

A red scanner is a finding about a package this project installs. Update the package (a
Dependabot `uv` or `npm` PR, a Security Fixes PR, or a hand-run
`uv lock --upgrade-package`); never relax the scanner — that is weakening a gate (AGENTS.md's
"Security and human approval").
